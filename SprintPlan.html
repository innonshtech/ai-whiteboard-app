⚡ Sprint 1 — Foundation
Week 1–2  |  10 working days  |  Stories #1–#16
🎯 Sprint Goal: The platform has a working foundation — any user can register, log in, be assigned a role, and land on their correct dashboard. The Super Admin can register a school and generate a panel license key. The IFP panel can boot and connect to the backend.
📺 Demo checkpoints: Week 1 Demo — Login working for all 3 roles (Admin, Teacher, Student) Week 2 Demo — School registration + panel license generation + panel boots and connects
#1
Email & OTP Login
Auth · M14
A user (teacher, student, admin) opens the app or panel and logs in using their registered email address and a one-time password (OTP) sent to their email. The system verifies the OTP, creates a session, and redirects the user to their role-specific dashboard.
Acceptance Criteria
  • User enters email → system sends 6-digit OTP to that email within 30 seconds
  • OTP expires after 5 minutes — expired OTP shows a clear error with a resend option
  • On valid OTP → JWT access token and refresh token are issued
  • On invalid OTP → error message shown, user can retry up to 3 times
  • After 3 failed attempts → account is temporarily locked for 15 minutes
  • Successful login → user redirected to their role dashboard (Admin / Teacher / Student)
  • JWT access token expires in 15 minutes, refresh token in 7 days
📊 Login Flow
flowchart TD A[User enters email] --> B[Backend sends OTP to email] B --> C[User enters OTP] C --> D{OTP valid?} D -->|Yes| E[Issue JWT + Refresh Token] D -->|No| F{Attempts < 3?} F -->|Yes| G[Show error — retry] F -->|No| H[Lock account 15 min] E --> I[Redirect to role dashboard]
#2
Google SSO Login
Auth · M14
A user clicks "Sign in with Google" and is redirected to Google's OAuth consent screen. After approving, they are returned to the app and logged in automatically. If it's their first login via Google, a new account is created using their Google email.
Acceptance Criteria
  • Google OAuth button is visible on all login screens (Panel, Teacher App, Student App, Admin)
  • Clicking it opens Google's OAuth consent screen
  • On approval → backend receives Google token, verifies it, creates or fetches user record
  • New user created with role = pending (Super Admin assigns role after first login)
  • Returning user → logged in directly, redirected to dashboard
  • If Google auth fails → clear error message shown
#3
Role-Based Access Control (RBAC)
Auth · M14
The system has 4 roles — Super Admin, School Admin, Teacher, Student/Parent. Each role sees only what they are allowed to see. A teacher cannot access admin pages. A student cannot access teacher pages. Role is assigned at account creation and stored in the JWT.
Acceptance Criteria
  • 4 roles defined: SUPER_ADMIN, SCHOOL_ADMIN, TEACHER, STUDENT
  • Role is embedded in JWT payload on login
  • Every API route has a role guard — unauthorized access returns 403
  • Frontend routes are protected — wrong role redirects to "Access Denied" page
  • Super Admin can view and change any user's role
  • Role change takes effect immediately on next login (existing session not affected)
#4
Two-Factor Authentication (2FA)
Auth · M14
A user can optionally enable 2FA on their account. Once enabled, after entering their password/OTP, they are asked for a 6-digit TOTP code from their authenticator app (Google Authenticator, Authy). 2FA can be enabled/disabled from account settings.
Acceptance Criteria
  • User can enable 2FA from settings — system shows QR code to scan with authenticator app
  • User confirms setup by entering first TOTP code — only then is 2FA activated
  • On login with 2FA enabled → after OTP step, user is prompted for TOTP
  • Valid TOTP → login succeeds. Invalid TOTP → error, user can retry
  • User can disable 2FA from settings by entering their current TOTP
  • Backup codes (8 codes) provided on 2FA setup for emergency access
#5
QR Code Login (Panel)
Auth · M14 · Panel
A teacher walks up to the IFP panel and instead of typing their email, they open the GYOASH Teacher App on their phone, tap "Login to Panel", and scan the QR code shown on the panel screen. The panel logs them in instantly.
Acceptance Criteria
  • Panel login screen shows a QR code that refreshes every 60 seconds
  • Teacher App shows a QR scanner when "Login to Panel" is tapped
  • On successful scan → panel receives the teacher's auth token and logs them in
  • If QR code has expired → panel shows "QR expired — refreshing" message
  • QR login only works for TEACHER role — students and admins cannot use it
  • Panel session is tied to the teacher — logging out on the app also logs out the panel
📊 QR Login Flow

#6
Audit Logs
Auth · M14
Every significant action in the system (login, logout, role change, license key generation, panel lock/unlock, content blocking change) is recorded in an audit log. Super Admin can view and filter the audit log from the admin portal.
Acceptance Criteria
  • Audit log records: action type, user ID, role, IP address, timestamp
  • Actions logged: login, logout, failed login, role change, school created, panel locked, license generated
  • Super Admin can view audit log with filter by date, user, action type
  • Audit logs are read-only — no one can delete or edit them
  • Logs are retained for minimum 90 days

#9
License Key Generation & Management
Admin · M10
Each IFP panel needs a unique license key to activate the GYOASH software. Super Admin generates license keys — one per panel. The key has an expiry date. Keys can be extended. Invalid or expired keys cause the panel software to show a "License expired" screen.
Acceptance Criteria
  • Super Admin can generate a license key for a specific school + classroom
  • Key format: GYSH-XXXX-XXXX-XXXX (16 chars with dashes)
  • Key has expiry date set at generation (default 1 year)
  • Super Admin can extend key validity by entering new expiry date
  • Panel software checks key validity on every startup and every 24 hours
  • Expired key → panel shows "License expired. Contact your administrator." and locks
  • Super Admin dashboard shows keys expiring in next 30 days as a warning

#33
FastAPI — AI Gateway Setup
AI Backend · M2
Before any AI tool can work, the FastAPI backend needs to be set up with the LLM gateway. This includes OpenAI and Gemini API integrations, a rate limiter to track token usage per school, a fallback mechanism (if OpenAI fails, use Gemini), and the internal proxy from Node.js to FastAPI.
Acceptance Criteria
  • FastAPI server runs on port 8000, accessible from Node.js backend via internal network
  • All requests to /ai/* require the internal FASTAPI_INTERNAL_SECRET header — unauthorized requests return 401
  • OpenAI GPT-4o is the default model. If OpenAI returns an error or timeout, automatically retry with Gemini
  • Token usage per school is tracked in the database (ai_logs table)
  • If a school exceeds their monthly token limit → return 429 with "AI quota exceeded" message
  • All AI endpoints have a 30-second timeout — return 408 if exceeded
  • GET /ai/health returns 200 — used by Node.js to check FastAPI is alive
📊 AI Request Flow
